**Чистая архитектура** — это **способ организации кода, который способствует строгому разделению ответственности**. Приложение разбивается на независимые функциональные компоненты, которые взаимодействуют друг с другом определённым способом, при этом между ними передаются только те ресурсы, которые необходимы для выполнения поставленной задачи.

**Основная цель чистой архитектуры** — создавать системы, которые: 
- **Удобны в обслуживании**. Легко поддаются пониманию и модификации, что позволяет разработчикам вносить изменения с минимальным риском внесения ошибок.
- **Тестируемы**. Разработаны таким образом, чтобы тестирование было простым, что позволяет создавать автоматизированные тесты для различных частей системы.
- **Независимы от фреймворков**. Фреймворки могут быть заменены с минимальным воздействием на систему. 
- **Независимы от пользовательского интерфейса**. Пользовательский интерфейс может изменяться, не влияя на базовую логику или бизнес-правила. 
- **Независимы от базы данных**. Механизмы хранения и поиска данных могут изменяться, не затрагивая систему. 
- **Независимы от внешнего влияния**. Бизнес-правила не привязаны к каким-либо конкретным деталям реализации, что делает систему легко адаптируемой к изменениям. 

### Принципы чистой архитектуры
#### **Разделение на уровни**: 
	- Уровень представления (UI) - взаимодействие с пользователем и обработка запросов.
	- Уровень приложения - бизнес логика и координация работы между уровнями представления и домена.
	- Уровень домена (domain) - бизнес логика и компоненты, отвечающие за работу с данными.
    - Уровень инфраструктуры - поддержка структур приложения и связь с внешними системами (например бд, внешние API и тд).

### Ключевые аспекты архитектуры приложения
- **Логическое разделение:**
	- Слой представления (UI) - отвечает за отображение данных, обработку взаимодействия с пользователем.
	- Слой бизнес логики - хранит основные правила, операции, связанные с предметной областью.
	- Слой доступа к данным - работа с базами данных, файловыми системами, внешними API.
- **Взаимодействие между слоями**
	- Какие интерфейсы используются, какие объекты или DTO(Data Transfre Objects) передаются.
- **Паттерны проектирования**
	- MVC, MVP, MVVM - в случае фронтенд-приложений или гибридных систем.
	- Domain-Driven Design (DDD) - отделение сущностей, агрегаций, доменных сервисов от инфраструктуры.
	- [[Слойная архитектура]] (Layerd Architecture) - классический подход "представление -> домен -> инфраструктура"
- **Технологический стек**
	- Конкретный фреймворк, язык или runtime, определяющий, как структурируются модули (например Django для Python, Spring для Java, ASP.NET для C#, Qt для C++ и тд.).


### Инструменты описания архитектуры приложения
- **UML-диаграммы**
	 - (Component Diagram, Package Diagram) - показывают, какие компоненты или пакеты существуют в приложении и как они связаны.
- **С4-модель**
	- (Container  Component Views) - можно детализировать контейнер (приложение) на уровень компонентов (модули, библиотеки).
- **Архитектурные решения (ADR)**
	- краткие записи о том, посему выбраны те или иные паттерны, структуры данных, библиотеки.


На границе каждого слоя должны быть интерфейсы (порты), через которые слои обмениваются информацией
Разработка простого приложения на чистой архитектуре это overigeneering, поэтому количество слоев можно изменять:
1) Правило пересечения границ слоев - границы пересекают модели dto
2) Слой бизнес логики не зависит ни от чего - то есть взаимодействует через остальные только через интерфейсы
3) Приоритет внутреннего слоя - внутренний слой определяет интерфейс, по которому он будет взаимодействовать с внешним слоем
